# Product-attributes migration: runbook

Covers `apps/api/src/database/migrations/1792865771843-AddProductAttributes.ts`
(the additive migration), `apps/api/src/database/cli-data-source.ts` (the
explicit-`DATABASE_URL`-only CLI entry point), and where this fits relative
to the **actual** production release path.

## 0. Deployment path correction (read this first)

`render.yaml` at the repo root is **not** how this API actually deploys —
it is unused by the real release path and must not be relied on for
anything, including `TYPEORM_SYNCHRONIZE`. Verified by reading the real
path end to end:

- `.github/workflows/deploy-api-vps.yml` builds a signed artifact
  (`scripts/production/package-api.sh`) and ships it over a
  Tailscale-only SSH channel to a self-hosted VPS, to a narrowly
  restricted `rad-deploy` account whose forced command
  (`scripts/production/rad-deploy-ssh-entrypoint.sh`) accepts nothing but
  a fixed `deploy kind=api commit=<sha> run_id=<n> run_attempt=<n>`
  grammar and hands the request to a root-owned broker.
- That broker, `scripts/production/rad_release.py`, is the real
  authority. Its `api_preflight()` **refuses to release at all** unless
  the production env file (`/etc/rad/api.env`) has
  `NODE_ENV=production` and `TYPEORM_SYNCHRONIZE=false` set explicitly
  (see `api_preflight`'s `value("TYPEORM_SYNCHRONIZE") == "false"`
  check), and refuses if the systemd unit has any `ExecStartPre`/
  `ExecStartPost`/`ExecCondition` hook — specifically to prevent the
  legacy `start-production.mjs` wrapper (which would run `sync-schema.ts`)
  from ever executing in production. `ExecStart` runs `dist/main.js`
  directly, with nothing before it.
- **Net effect: production has no schema-sync path at all, automatic or
  otherwise, and no automated migration step either.** A schema change
  only ever reaches production because an operator deliberately ran one,
  by hand, against `DATABASE_URL`. This document is that deliberate step
  for this change.

## 1. What this migration does

Adds exactly four new tables — `ProductAttribute`, `ProductAttributeOption`,
`ProductAttributeCategory`, `ProductAttributeValue` — with their keys,
indexes, unique constraints and foreign keys (see the migration file for
the exact DDL; it was generated by `typeorm migration:generate`, diffing
the entities against a database that already had every other table, then
hand-reviewed). No existing table, column, row, or constraint is touched.
Old application code never queries these tables, so they can exist, be
empty, or be populated without affecting anything that doesn't already
know about them.

## 2. Preflight — obtain and inspect the artifact (any time, read-only)

Use the **exact artifact CI will release**, not a local build, so what you
migrate against matches what the release broker verifies and ships:

```bash
# From a machine with `gh` authenticated against this repo:
gh run list --workflow=deploy-api-vps.yml --branch=main --limit=5
gh run download <run-id> --name "api-release-<commit-sha>-<run-attempt>" --dir ./rad-migrate-stage
```

This downloads `api-release.tar.gz`, `release.json`, `release.sigstore.json`
for the exact commit being released. (Optional) verify its provenance the
same way the broker does:

```bash
gh attestation verify ./rad-migrate-stage/api-release.tar.gz \
  --repo mahdiyehnorouzi/RAD --signer-workflow mahdiyehnorouzi/RAD/.github/workflows/deploy-api-vps.yml
```

Copy the tarball to the VPS over **your own** root/operator SSH session
(not the `rad-deploy` CI-only account, which only accepts the fixed
`deploy kind=...` release trigger and cannot be used to stage files
separately):

```bash
scp ./rad-migrate-stage/api-release.tar.gz root@<vps-host>:/root/rad-migrate-stage.tar.gz
ssh root@<vps-host>
mkdir -p /root/rad-migrate-stage && tar -xzf /root/rad-migrate-stage.tar.gz -C /root/rad-migrate-stage
cd /root/rad-migrate-stage/apps/api
```

This exact sequence (build → prune --omit=dev → package-api.sh → extract →
`npm run migration:run` from the extracted `apps/api`) was run end to end
in review against an isolated, disposable Postgres seeded to look like a
**pre-feature production database** (every other table present, these four
absent, with an existing `Product` row) — not just against a dev checkout.
`tsx` and `typeorm` are regular `dependencies` of `apps/api` (not
`devDependencies`), so they survive `npm prune --omit=dev` and are present
in the real artifact; `migration:run` was confirmed to run from that exact
extracted tree, and the compiled `dist/main.js` (started exactly as the
real systemd `ExecStart` does — no wrapper, `TYPEORM_SYNCHRONIZE=false`)
booted healthy against the migrated database afterward.

## 3. Verify you're pointed at the right database

On the VPS, as root (the only account permitted to read
`/etc/rad/api.env` — it's root-protected, by the same invariant the
release broker itself enforces):

```bash
set -a; source /etc/rad/api.env; set +a
echo "$DATABASE_URL" | sed -E 's#://[^@]+@#://<redacted>@#'   # sanity-check the host, never print credentials
psql "$DATABASE_URL" -c "\dt"
psql "$DATABASE_URL" -c 'SELECT count(*) FROM "Product";'
```

Confirm this is actually the production database you expect (table list,
row counts), not a stray local/staging one.

## 4. Backup (always, before any DDL, no exceptions)

```bash
pg_dump --dbname="$DATABASE_URL" --format=custom \
  --file="rad-pre-product-attributes-$(date -u +%Y%m%dT%H%M%SZ).dump"

# Verify the dump is actually restorable BEFORE trusting it (into a
# throwaway database, never back into production):
createdb rad_restore_check
pg_restore --dbname=rad_restore_check "rad-pre-product-attributes-....dump"
psql rad_restore_check -c 'SELECT count(*) FROM "Product";'   # compare to step 3's count
dropdb rad_restore_check
```

Store the `.dump` file somewhere durable, off the VPS, before proceeding.
As with every prior migration in this repo (see `docs/db-migration-runbook.md`),
**this backup is the only database rollback path** — see §7.

## 5. Run the migration — `DATABASE_URL` required explicitly, no fallback

```bash
cd /root/rad-migrate-stage/apps/api   # the extracted artifact from §2, NOT your laptop checkout
set -a; source /etc/rad/api.env; set +a
npm run migration:run
```

Two independent guards make this safe against the classic "forgot to set
the env var" mistake, both enforced in
`apps/api/src/database/cli-data-source.ts`, verified directly:

- **No `DATABASE_URL` at all** → throws immediately, before attempting any
  connection. It never falls back to the local dev default
  (`postgresql://rad:rad@localhost:5432/rad`) the way the app's own boot
  path (`createAppDataSource`) does.
- **`DATABASE_URL` pointing anywhere non-local** (which production always
  is) **without `RAD_ALLOW_REMOTE_DB_WRITE=<exact hostname>` also set** →
  throws, via `assertSafeScriptTarget`, the same guard every other
  data-mutating script in this repo already uses
  (`apps/api/scripts/db-migrate-seaweedfs-catchup.ts`). Since `/etc/rad/api.env`
  already names the real host, this is normally satisfied by also
  exporting `RAD_ALLOW_REMOTE_DB_WRITE=<that same host>` — naming the host,
  not just "yes", so a copied/exported env var can never silently
  authorize a different target later.

A missing or wrong `DATABASE_URL` cannot result in the migration silently
running somewhere unintended — it refuses outright, both times.

Expect output ending in `Migration AddProductAttributes... has been
executed successfully.` Everything runs inside one transaction; a failure
at any point rolls back entirely (Postgres DDL is transactional) and the
database is exactly as it was before.

## 6. Postflight — verify the schema and the data

```bash
# Confirm no further drift (this writes a throwaway migration FILE if there
# is drift — do not commit it; delete it after inspecting, `npm run
# migration:run` already told you whether it succeeded):
npm run migration:generate -- src/database/migrations/PostflightCheck
# Expect: "No changes in database schema were found - cannot generate a migration."
# If it DOES generate a file, STOP: that's unexpected drift, not this
# migration — inspect the generated file before doing anything else, then
# `rm` it (never commit a migration generated against production).

psql "$DATABASE_URL" -c 'SELECT count(*) FROM "Product";'   # same as step 3 — must be unchanged
psql "$DATABASE_URL" -c '\dt "Product*"'                     # the 4 new tables now present, empty
```

## 7. Rollback behavior — never drops a populated attribute table

**Database rollback and application/code rollback are two separate
concerns, on purpose** — same philosophy as every prior migration in this
repo (`docs/db-migration-runbook.md`):

- **Code rollback** (the release broker's own automatic rollback on a
  failed health check, or a later manual rollback via
  `scripts/rollback-api-systemd.sh`) **never touches the database** and
  needs no special handling here: old code never references these four
  tables, so whether they exist, are empty, or already hold real
  admin-entered attributes makes no difference to code that doesn't know
  they exist. No action is ever required on the database side just
  because the API code was rolled back.
- **`npm run migration:revert`** (TypeORM's built-in undo, which
  unconditionally `DROP TABLE`s all four) **must never be run against a
  database once an admin may have created a real attribute or a product
  may have a real saved value.** It exists for undoing this migration
  *before* it has ever reached a database anyone uses it against — a
  local/dev/CI database, or this same production run, reverted within the
  same maintenance window, before step 5 ever returned success and before
  any admin has touched the new "ویژگی‌های محصول" section. Once real data
  might exist, dropping these tables to "undo" is exactly the mistake the
  rest of this repo's migration tooling is built to prevent (see the
  `down()` method's own comment in the migration file, and
  `db-migration-runbook.md`'s identical rule for the SeaweedFS migration).
- **The only safe database rollback once real data may exist** is
  restoring the §4 backup into a fresh database for inspection, and making
  an explicit, separate decision about any writes that happened between
  the backup and the restore — never restoring over the live database
  blind, and never `DROP TABLE`.
- **If you decide not to proceed with the API release after step 5**: no
  action needed. The four new, empty (or now-populated) tables are inert
  until the new API code is actually running — nothing reads or writes
  them before that.

## 8. Deployment order

1. **Backup** (§4).
2. **Run the migration** (§5, §6) — code that depends on these tables is
   not running yet, so there is no window where half-migrated schema
   meets code that needs it.
3. **Trigger the normal, unmodified release** —
   `gh workflow run deploy-api-vps.yml -f confirm=deploy -f commit_sha=<sha>`
   (same commit the artifact in §2 was built from). Nothing about the
   release broker itself needed to change for this migration; it was
   deliberately kept out of this PR's scope (`scripts/production/rad_release.py`
   is a root-owned, hash-pinned file that requires its own separate
   re-approval for any change — adding automatic migration execution to it
   is a larger, separate decision, not bundled into a feature PR).
4. **Verify**: open the admin panel, create a test attribute, assign it to
   a category, save a product with a value, confirm it shows on the
   storefront — the actual end-to-end proof this was built for.

## Remaining operator steps for this PR

Nothing above has been run against the real VPS or production database —
only against disposable, isolated Postgres instances (Docker containers on
ports outside production's reach) using the exact packaged artifact. Before
merging/releasing this PR, an operator with real VPS access must:

1. Run §2–§6 against the real production `DATABASE_URL`, from the VPS, using
   the artifact for the commit about to be released.
2. Confirm §6's postflight checks pass against the real database.
3. Only then trigger the normal `deploy-api-vps.yml` release for that same
   commit.

No step in this document grants itself permission to touch production —
each command above must be run deliberately, by a human with real
production access, after reading this file.
