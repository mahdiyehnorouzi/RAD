**Entry points**
- `apps/storefront/app/[locale]/products/(list)/page.tsx` — listing page
- `apps/storefront/app/[locale]/products/[slug]/page.tsx` — PDP
- `apps/storefront/app/[locale]/products/[slug]/qr/page.tsx` — QR landing

**API endpoints** (`apps/api/src/catalog/catalog.controller.ts`, no `@UseGuards`, public)

- `GET /products/:slug` → `CatalogService.bySlug`
- `GET /products/:slug/related` → `CatalogService.related`
- `GET /search?q=&locale=` → `CatalogService.search`

**Service/logic**: `apps/api/src/catalog/catalog.service.ts`, `catalog.query.ts`,
`product.mapper.ts`, `artwork.mapper.ts`, `rad-number.ts`.

**Entities**: `Product` (`apps/api/src/database/entities/product.entity.ts`),

(inventory.service.ts:71-75) decides whether catalog surfaces a product —

catalog service only reads, never writes, `Product.status`, consistent with

**Tests**: `apps/api/src/catalog/catalog-image-select.spec.ts`,

## 2. Cart

**Entry point**: `apps/storefront/app/[locale]/cart/page.tsx`, composed from
`apps/storefront/features/cart/cart-page/*` (`cart-page.tsx`, `cart-line.tsx`,
`cart-hold.tsx`, `cart-released.tsx`), state in
`apps/storefront/features/cart/cart-provider.tsx`.

**API endpoints** (`apps/api/src/cart/cart.controller.ts`, no guard — identity
resolved per-request via `IdentityService`, works for guests and logged-in
users via `ownerKey`):
- `GET /cart` → `CartService.get`
- `POST /cart/items` (`AddCartItemDto`, `apps/api/src/cart/dto/add-item.dto.ts`) → `CartService.add`
- `DELETE /cart/items/:slug` → `CartService.remove`
- `DELETE /cart` → `CartService.clear`

**Service/logic**: `apps/api/src/cart/cart.service.ts`. Adding to cart calls
`InventoryService.hold(ownerKey, slug)` (inventory.service.ts:137-158), which
atomically flips `Product.status: available → sold` with `holdExpiresAt` /
`heldBy`, i.e. the unique-product reservation begins at **add-to-cart**, not
at checkout. `remove`/`clear` call `releaseCartHolds` inside a transaction so
the DB row for the cart item and the hold release stay consistent.

**Entities**: `CartItem` (`apps/api/src/database/entities/cart-item.entity.ts`),
`Product`.

**Auth**: none required; identity is resolved from cookie session or guest
key (`apps/api/src/common/identity.service.ts`, not read in depth this pass —
flag for Phase 2 if guest/session merging matters).

**State transitions**: `Product.status`: `available → sold` (holdExpiresAt =
now + `CART_HOLD_MS`) on add; back to `available` on remove/clear or on the
periodic sweep (`InventoryService.releaseExpiredHolds`, run every
`HOLD_SWEEP_INTERVAL_MS` and opportunistically on most cart/order operations).

**Business rule confirmed**: no quantity field anywhere in `CartItem` or
`AddCartItemDto` — matches AGENTS.md §5 ("no quantity logic for 1/1 unique
products").

**Known/likely discrepancies**: none observed. `CartService.add` does not
re-validate price staleness beyond snapshotting `tomanPriceAtAdd` /
`usdPriceAtAdd` at add time; checkout re-reads the live `Product.tomanPrice`
inside its own transaction (orders.service.ts:135-158), so the snapshot in
`CartItem` is informational/UI-display only, not the priced source of truth —
worth confirming the storefront cart page doesn't display the stale snapshot
as if it were final pricing without re-fetching before checkout.

**Tests**: no dedicated `cart.spec.ts` found. Cart-hold behavior is partly
exercised indirectly through `apps/api/src/inventory/inventory.spec.ts` (hold
sweep timer behavior only) and through `purchase-flow.spec.ts`'s cart→checkout
setup steps, but there is no isolated unit test of `CartService` itself.

## 3. Checkout → payment receipt → admin review lifecycle

**Entry points**
- `apps/storefront/app/[locale]/checkout/page.tsx` — checkout form (address/
  phone/policy acceptance)
- `apps/storefront/app/[locale]/checkout/[id]/page.tsx` → renders
  `CheckoutPayment` (`apps/storefront/components/checkout/checkout-payment/`)
  for receipt submission, including
  `apps/storefront/components/checkout/checkout-payment/payment-receipt.tsx`
- `apps/storefront/app/[locale]/orders/[id]/page.tsx` — order detail / resubmit
  receipt via `apps/storefront/components/orders/order-detail/receipt-form.tsx`

**API endpoints** (`apps/api/src/orders/orders.controller.ts`, no `@UseGuards`
decorator — identity resolved per-request, ownership enforced at the service
layer via `ownerKey` lookups):
- `GET /orders` → `OrdersService.list`
- `GET /orders/:id` → `OrdersService.get`
- `POST /orders` (`CheckoutDto`) → `OrdersService.checkout`
- `POST /orders/:id/confirm-payment` (`ConfirmPaymentDto`,
  `apps/api/src/orders/dto/confirm-payment.dto.ts`) → `OrdersService.confirmPayment`
- `POST /orders/:id/demo-pay` — same DTO/handler as confirm-payment, kept as a
  `@deprecated` alias (`confirmDemoPayment`, orders.service.ts:340-347)
- `POST /orders/:id/cancel` → `OrdersService.cancel`

Admin side (`apps/api/src/admin/admin.controller.ts`, `@UseGuards(AdminGuard)`):
- `GET /admin/orders` → `AdminService.listOrders`
- `PATCH /admin/orders/:id` (`UpdateOrderDto`) → `AdminService.updateOrder`
  (requires `admin.assert(adminRole, "order.write")`)
- `POST /admin/orders/:id/payment/approve` → `AdminService.approvePayment` →
  delegates to `PaymentReviewService.approve`
- `POST /admin/orders/:id/payment/reject` (`RejectPaymentDto`) →
  `AdminService.rejectPayment` → `PaymentReviewService.reject`

**Service/logic files**
- `apps/api/src/orders/orders.service.ts` (checkout, confirmPayment, cancel)
- `apps/api/src/orders/payment-receipt.ts` (`normalizeTrackingNumber`,
  `normalizePhone`, `receiptHash`)
- `apps/api/src/orders/payment-review.service.ts` (admin approve/reject —
  note: lives under `orders/`, not under `admin/` as AGENTS.md's prose
  suggests; `AdminService` imports it from `../orders/payment-review.service`)
- `apps/api/src/inventory/inventory.service.ts` (all `Product.status` writes)
- `apps/api/src/common/image-data.ts` (`assertImageData`, size/type limits —
  not opened this pass, flagged for Phase 2 if receipt format bugs surface)

**Entities**: `Order`, `OrderItem`, `PaymentIntent`, `Product`, `CartItem`
(cleared on checkout), `User` (for email notification lookup in
`PaymentReviewService.notify`).

**Auth**: `OrdersController` has no guard — any identity (including guest)
can check out/pay/cancel, with ownership scoped by `ownerKey` inside the
service (`ownedOrder`, `lockOwnedOrder`). Admin endpoints require
`AdminGuard` (`apps/api/src/common/guards/admin.guard.ts`) — checks
`request.userId` is set, loads the `User`, requires `user.adminRole` truthy
and `user.status === "active"`, then additionally `AdminService.assert(role,
"order.write")` per-endpoint for writes (role-based fine-grained permission,
defined in `apps/api/src/admin/permissions.ts`, not opened this pass).

**State transitions** (`apps/api/src/orders/const/order-status.ts`):
`STORE_ORDER_STATUSES = pending_payment → pending_verification → confirmed →
packing → shipped → delivered`, with terminal branches `expired`, `rejected`,
`cancelled`, `returned`. `MANUAL_ORDER_TRANSITIONS` explicitly excludes
`confirm`/`reject` from the generic admin order editor — those only happen via
the two dedicated payment endpoints (comment at order-status.ts:29-32
confirms this is intentional).

`PaymentIntent.status`: `created → redirected?` (if a redirect-style provider
session starts, orders.service.ts:204-223) `→ submitted → verified|rejected`,
or `→ failed` (cancel/expiry).

**Verification against AGENTS.md §5 claims — all confirmed present in code**:
- Checkout creates `Order(pending_payment)`, `OrderItem`s, `PaymentIntent(created)`,
  reserves inventory for `ORDER_PAYMENT_WINDOW_MS` (30 min) — orders.service.ts:134-202,
  `ORDER_PAYMENT_WINDOW_MS = 30 * 60 * 1000` in `orders/const/order-status.ts`. ✅
- `confirmPayment` validates image, normalizes tracking number, moves
  `pending_payment → pending_verification`, `PaymentIntent → submitted` —
  orders.service.ts:238-338. ✅
- Admin approve → `Order: confirmed`, `PaymentIntent: verified`, product
  `markSold` — payment-review.service.ts:31-61. ✅ (also sets
  `estimatedDeliveryAt` default +6 days if not already set)
- Admin reject → `Order: rejected`, `PaymentIntent: rejected`, product
  restocked via `InventoryService.restock` — payment-review.service.ts:63-90. ✅

**Verification of the five `confirmPayment` protections claimed in AGENTS.md §5 —
all present in `orders.service.ts`**:
1. Idempotent resubmission: `isIdenticalResubmit` check, lines 287-291. ✅
2. Duplicate receipt/tracking detection across other orders:
   `assertReceiptNotReused` (SHA-256 `receiptHash`, checks both hash and
   tracking number against other orders' `submitted`/`verified` intents),
   lines 301-306 & 426-457. ✅
3. Submission cap `MAX_RECEIPT_SUBMISSIONS = 5`, line 47 & 294-300. ✅
4. State validation `assertCanSubmitReceipt` — expired/rejected/
   cancelled/returned/already-confirmed all explicitly rejected with
   structured codes (`order_expired`, `order_rejected`, `order_closed`,
   `order_already_confirmed`), lines 385-423. ✅
5. Row-level `pessimistic_write` lock on the `Order` row for the whole
   transaction via `lockOwnedOrder`, lines 270, 460-476. ✅

**Tracking number two-layer rule — confirmed, and frontend already mirrors it
correctly**:
- DTO (`confirm-payment.dto.ts:18-26`) only enforces `@MaxLength(40)`, with an
  explicit comment that this is a sanity bound, not the real rule.
- Real rule lives in `normalizeTrackingNumber` (`payment-receipt.ts:13-16`):
  strip spaces/dashes, uppercase, require `^[A-Z0-9]{4,32}$` after converting
  Persian/Arabic digits to Latin.
- Frontend mirrors the exact same regex independently in
  `apps/storefront/lib/payment/receipt.ts:14-17`
  (`normalizeTrackingNumber`) — **no discrepancy found here**; this is a case
  where AGENTS.md's warning is already correctly heeded in the current code,
  not a violation to fix. (Two independent implementations of the same regex
  is itself a minor duplication risk — see Discrepancies section.)

**Error handling**: structured codes observed: `receipt_required`,
`receipt_invalid`, `tracking_invalid`, `payment_missing`, `receipt_limit`,
`receipt_duplicate` (409 Conflict), `order_expired`, `order_rejected`,
`order_closed`, `order_already_confirmed`, `order_not_found`. All carry
Persian `message` text, matching AGENTS.md §6.

**Tests**: `apps/api/src/orders/purchase-flow.spec.ts` — extensive, 13 named
`test()` cases covering: receipts without tracking + duplicate-image
blocking; full happy path cart→checkout→receipt→approve→confirmed→unavailable;
concurrent-buyer race (only one reaches payment); correct-receipt doesn't
expire; duplicate receipt/tracking across orders rejected; admin reject with
reason; invalid receipt format rejected; resubmission while pending
verification; idempotent double-click resubmission; two-buyers-one-product
race; reject-then-restock-then-rebuyable; 30-minute expiry; policy-acceptance
requirement and version persistence. `apps/api/src/inventory/inventory.spec.ts`
covers the hold-sweep concurrency/timer behavior underlying this flow. Git
status at the start of this session showed this spec file as **unmodified**
(no uncommitted diff), contrary to AGENTS.md's note that it "was already
modified ... as of this audit" — worth flagging as a possibly stale note in
AGENTS.md itself (see Discrepancies).

## 4. Custom order submission flow (commissions / "studio")

**Entry points**
- `apps/storefront/app/[locale]/studio/page.tsx`, `studio/start/page.tsx` →
  `apps/storefront/features/studio/` (`CustomOrderStart` component — directory
  not expanded further this pass)
- Customer-facing commission tracking presumably under `account` or a
  dedicated route — not located in this pass; flag for Phase 2 (searched only
  `studio/` and `shape/`).

**API endpoints** (`apps/api/src/commissions/commissions.controller.ts`, no
guard decorator — identity-scoped like cart/orders):
- `GET /commissions` → `listMine`
- `GET /commissions/workshop` → `listWorkshop`
- `PUT /commissions/workshop/:id` (`SaveCommissionDto`) → `saveWorkshop`
- `GET /commissions/:id` → `getMine`
- `POST /commissions` (`CreateCommissionDto`) → `create`
- `PUT /commissions/:id` (`SaveCommissionDto`) → `saveMine`
- `POST /commissions/:id/messages` (`CommissionMessageDto`) → `addMineMessage`

Admin side (`admin.controller.ts`, `AdminGuard` + `order.write` permission):
- `GET /admin/commissions`, `GET /admin/commissions/:id`
- `PATCH /admin/commissions/:id` → `saveAdmin`
- `POST /admin/commissions/:id/review` → `beginReview`
- `POST /admin/commissions/:id/decide` (`CommissionDecideDto`) → `decide`
- `POST /admin/commissions/:id/messages` (`CommissionMessageDto`) →
  `addArtistMessage(id, body, internal)`

**Service/logic**: `apps/api/src/commissions/commissions.service.ts`,
`commission.factory.ts`, `commission.mutate.ts`, `commission.types.ts`.

**Entities**: `Commission` (`apps/api/src/database/entities/commission.entity.ts`)
— notably stores its entire domain model as a single `jsonb` column
(`payload: unknown`), with no relational columns beyond `id`/`ownerKey`/
timestamps. All validation of the payload shape therefore happens in
TypeScript (`commission.types.ts`, `commission.mutate.ts`), not at the
database layer.

**State machine** (`commission.types.ts:5-16`, `MakingStageId`):
`design_submitted → feasibility → quote → approval_deposit → making →
pre_kiln → firing → reveal → shipping → complete`, with a `declined` terminal
branch. `NextActor: "customer" | "artist" | "none"` tracks whose turn it is.
Each commission also carries its own `changeRequests[]` (status `open |
accepted | withdrawn`), `messages[]`/`internalNotes[]` (artist-only), and an
`audit[]` trail — all inside the same jsonb blob.

**Auth note**: like cart/orders, the customer-facing `CommissionsController`
has no `@UseGuards`; ownership is presumably enforced by `ownerKey` filtering
inside `CommissionsService.listMine/getMine/saveMine/addMineMessage` (not
opened line-by-line this pass — **flag for Phase 2**: confirm `getMine`
actually filters by `ownerKey` and doesn't allow fetching another customer's
commission by guessing/enumerating `id`, since AGENTS.md lists "order
ownership" as high-risk).

**Known/likely discrepancies**:
- Business rules for the making-stage state machine (e.g. which actor may
  advance which stage, whether `decide`/`beginReview` enforce
  `canTransitionStage`-style guards) are not yet verified against
  `commission.mutate.ts` — only the type shape was read. This is the biggest
  open question in this flow for Phase 2.
- The entire commission domain lives in untyped `jsonb`; a schema/version
  migration or partial update bug would not be caught by TypeORM at the
  entity level — correctness depends entirely on `commission.mutate.ts`'s
  discipline. Worth a focused review before touching anything in this path.

**Tests**: no commission-specific `.spec.ts` file found anywhere under
`apps/api/src/commissions/`. This flow currently has **no automated test
coverage** at all — notable gap given its state-machine complexity.

## 5. Messaging system (storefront ↔ admin)

Two independent messaging subsystems exist; do not conflate them.

### 5a. Contact messages (general inbox, optionally linked to an order)

**Entry point**: `apps/storefront/app/[locale]/contact/page.tsx`.

**API** (`apps/api/src/contact/contact.controller.ts`, no guard, rate-limited
with `@Throttle`):
- `POST /contact/messages` (5/min) → `ContactService.create`
- `POST /contact/messages/:id/reply` (10/min) → `ContactService.replyAsCustomer`
- `GET /contact/messages?orderId=` → `ContactService.listThreadsForOrder`

Admin side (`admin.controller.ts`, `AdminGuard`):
- `GET /admin/messages` → `ContactService.listAll`
- `PATCH /admin/messages/:id` (`UpdateContactMessageDto`) → `setStatus`
  (requires `order.write` — reuses the orders permission for message status,
  worth confirming that's intentional rather than copy-paste)
- `POST /admin/messages/:id/reply` (`ReplyContactMessageDto`) → `replyAsAdmin`
  (also gated on `order.write`)

**Service/logic**: `apps/api/src/contact/contact.service.ts`,
`contact.mapper.ts`, `order-reference.ts`, `contact-message-thread.migration.ts`.

**Entity**: `ContactMessage` (`apps/api/src/database/entities/contact-message.entity.ts`).
Thread model is intentionally flat: `rootId`/`parentId`, every reply
(admin or customer) points `parentId` at the thread's root, never chains
deeper (`findRoot`, contact.service.ts ~131-146).

**Notable logic**: `create()` optionally links a message to an `Order` by
reference number (`normalizeOrderReference`); if an `orderId` is given but no
matching order exists, it's a hard `BadRequestException` rather than silently
dropping the link. `fromOrderOwner` is computed server-side
(`order.ownerKey === ownerKey`) — the client cannot spoof "I own this order."

**Auth**: customer endpoints unguarded (ownerKey-scoped); admin endpoints
`AdminGuard` + `order.write`. `replyAsAdmin` comment explicitly notes "no
ownership check, gated by AdminGuard on the route" (contact.service.ts
~150-152) — intentional, since staff should be able to reply to any thread.

**Known/likely discrepancies**:
- `ContactService.replyAsCustomer` was not read this pass — need to verify it
  checks the caller actually owns the thread (via `ownerKey` or
  `fromOrderOwner`) before allowing a reply, otherwise a guest could reply
  into someone else's thread if they guess/obtain the message id. **Flag for
  Phase 2 as a priority check** — AGENTS.md lists "order ownership" as
  high-risk and this is adjacent to it.

**Tests**: no `contact.spec.ts` found. `apps/api/src/artist-applications/contact.spec.ts`
exists but that is for a different module (artist applications), not this
contact-message flow — **zero direct test coverage** for contact messaging.

### 5b. Commission messages (artist ↔ customer, within a commission)

Covered under Flow 4 above: `POST /commissions/:id/messages` (customer),
`POST /admin/commissions/:id/messages` (admin, with an `internal` flag for
staff-only notes per `commission.types.ts`'s `internalNotes`). Same
jsonb-backed storage, same lack of test coverage.

## 6. Admin order management

**Entry point**: `apps/admin` dashboard —
`apps/admin/components/admin-dashboard.tsx`,
`apps/admin/components/admin-order-payment.tsx` (receipt review UI),
`apps/admin/components/admin-order-messages.tsx`,

`apps/admin/lib/admin-data.ts`, `apps/admin/hooks/use-admin-workspace.ts`.
Note: `admin-dashboard.tsx`, `use-admin-workspace.ts`, and `admin-data.ts` all
show as modified in the current git working tree (per the session's git
status) — any Phase 2 change in this area should diff against the
**current working tree**, not assume it matches `main`.

**API endpoints**: see Flow 3 (`GET/PATCH /admin/orders`, payment
approve/reject) and Flow 5a (`GET/PATCH /admin/messages`, reply) — the admin
order screen is a composite of both plus damage reports
(`GET/PATCH /admin/damage-reports`, `DamageReportsService`, not opened this
pass).

**Auth**: `AdminGuard` on the whole `AdminController`, plus per-action
`this.admin.assert(request.adminRole, "<permission>")` calls
(`order.write`, `product.write`, `content.write`, `member.write`,
`product.delete`) — role/permission matrix lives in
`apps/api/src/admin/permissions.ts` (not opened this pass; flag for Phase 2 if
a role-escalation bug is suspected).

**`AdminOrderPayment` component** (`apps/admin/components/admin-order-payment.tsx`):
computes `reviewable = order.status === "pending_verification" && canWrite"`
— client-side gating mirrors the backend's `PaymentReviewService.lockForReview`
state check (only `pending_verification` is reviewable), which is good
belt-and-suspenders UX, but note AGENTS.md §5's warning that **UI state alone
never substitutes for backend enforcement** — confirmed here: the backend
(`lockForReview`, payment-review.service.ts:92-108) independently re-validates
status regardless of what the UI sent, so this is not a violation, just a
duplicate-of-truth worth being aware of when editing either side.

**Known/likely discrepancies**:
- `AdminService.updateOrder` and the payment approve/reject endpoints both
  touch `Order.status`, but only through different code paths
  (`MANUAL_ORDER_TRANSITIONS` vs `PaymentReviewService`). `updateOrder`
  itself was only located (admin.service.ts:252) not read in full — **Phase
  2 TODO**: confirm `updateOrder` actually calls `canManuallyTransitionOrder`
  before writing a new status, and cannot be used to bypass
  `MANUAL_ORDER_TRANSITIONS`'s exclusion of `confirmed`/`rejected` via a
  generic PATCH (i.e. that an admin can't PATCH status directly to
  `"confirmed"` without going through `/payment/approve` and its inventory
  side effects).

**Tests**: no `admin.service.spec.ts` or order-management-specific spec found
for the generic `updateOrder` path (only `orphan-upload.spec.ts`,
`replace-images.spec.ts`, `sign-auth.spec.ts` exist under `apps/api/src/admin/`,
all image/upload-related, not order-status related). The confirm/reject path
is indirectly covered via `purchase-flow.spec.ts` (Flow 3), but the generic
manual order-status editor (`PATCH /admin/orders/:id`) has **no test
coverage** found in this pass.

## Discrepancies / risks observed

1. **No test coverage for `CommissionsService`** — the entire custom-order
   state machine (`apps/api/src/commissions/commissions.service.ts`,
   `commission.mutate.ts`) has zero `.spec.ts` files. Given it's a jsonb-blob
   domain model with a 10-stage state machine and three actor roles, this is
   the single largest test-coverage gap found. (`apps/api/src/commissions/`)

2. **No test coverage for contact messaging** (`apps/api/src/contact/`) —
   `ContactService.replyAsCustomer`'s ownership check is unverified by reading
   or by tests. Recommend verifying this specific method early in Phase 2
   before any change in that area, per AGENTS.md's "order ownership" being a
   high-risk area (`apps/api/src/contact/contact.service.ts`).

3. **No dedicated `CartService` unit tests** — cart-hold-on-add and
   release-on-remove/clear logic (`apps/api/src/cart/cart.service.ts`) is only
   exercised indirectly as setup inside `purchase-flow.spec.ts`, not in
   isolation.

4. **No test coverage for `AdminService.updateOrder`** (generic manual
   order-status PATCH) — unverified whether it correctly refuses to write
   `confirmed`/`rejected` outside the two dedicated payment-review endpoints.
   `apps/api/src/admin/admin.service.ts:252` — read the method body before
   trusting `MANUAL_ORDER_TRANSITIONS` is actually enforced there.

5. **`AGENTS.md`'s own claim about `purchase-flow.spec.ts` being
   already-modified/uncommitted did not match observed git state** — `git
   status --short` on that file returned nothing at the start of this
   session, i.e. it is clean against `main`. Either the audit note in
   AGENTS.md is stale, or changes were committed since that audit was
   written. Worth a quick confirmation before Phase 2 touches that file, in
   case this reflects a timing gap rather than an error.

6. **Duplicated tracking-number regex** — the exact same business rule
   (`^[A-Z0-9]{4,32}$` after digit normalization) is implemented twice,
   independently, in `apps/api/src/orders/payment-receipt.ts:13-16` and
   `apps/storefront/lib/payment/receipt.ts:14-17`. They currently agree, but
   nothing enforces that they stay in sync — a future edit to one without the
   other would silently reintroduce the exact "frontend diverges from the
   real business rule" problem AGENTS.md §5 warns about. Not a current bug,
   but a latent one worth flagging rather than fixing silently (per AGENTS.md
   §11, scope discipline — this is out of scope for whatever Phase 2 task is
   assigned unless that task is specifically about this rule).

7. **Permission reuse in contact messaging** — `PATCH /admin/messages/:id`
   and `POST /admin/messages/:id/reply` are both gated on the `"order.write"`
   permission rather than a `message.write`/`content.write`-style permission
   of their own (`apps/api/src/admin/admin.controller.ts:147-165`). This may
   be intentional (messages are order-adjacent) or may be a copy-paste
   default — flag for confirmation rather than silent "fix."

8. **Unverified ownership on `CommissionsController`** — none of
   `listMine`/`getMine`/`saveMine`/`addMineMessage`
