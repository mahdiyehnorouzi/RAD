## 26 October 2026 additions

- **Issue 01 (Add to cart) reproduced and fixed.** Root cause: the cart/checkout `CatalogProvider` was seeded from `shopProducts()`, which drops any priced work without a real (non-placeholder) photo. A work correctly held in a buyer's cart but still missing its photos was invisible to `getProduct()` on the cart page, which rendered it as withdrawn/stale ("موجودی بعضی آثار تازه نشد") and blocked checkout even though the backend hold was fine. Reproduced against a real seeded sandbox database (isolated local Postgres, never the shared dev database on ports 3000/4000): added real zero-image priced products to a cart through the live API, then ran the actual `shopProducts`/`commerceProducts` functions against that response to confirm the before/after. Fix: `commerceProducts()` now backs cart/checkout lookup (keeps every priced work); `shopProducts()` keeps its existing photo filter for browsing/listing only. Commit `6ffd729`. Tests: `apps/storefront/lib/artworks/product.spec.ts`.
- **Issue 02 (inventory lifecycle) — effective status unified, not fully closed.** Admin and Storefront each re-derived available/reserved/sold independently, reading different wire shapes with no shared logic, and admin's hold check didn't compare against "now" (an expired-but-unswept hold could misreport as still in a customer's cart). Added `effectiveProductStatus()` to `@rad/types` as the one place that resolves `available | reserved | sold | unavailable`; storefront's `isReserved()` and admin's `productStatusLabel()`/`statusTone()` now resolve through it, and admin's product badges get a distinct "reserved" tone instead of sharing "sold"'s. The admin status *filter* dropdown still filters on raw status (lumps reserved + sold under "sold") — not yet addressed. Commit `3457a7a`. Tests: `packages/types/src/effective-product-status.spec.ts`, `apps/storefront/lib/catalog/product-status.spec.ts`, `apps/admin/lib/admin-data.spec.ts`, `apps/api/src/admin/admin-mapper-status.spec.ts`.

Verification for 01/02: `npm run typecheck:all` clean; `npm run test` (root, all workspaces) passing; `npm run test:media` in `apps/api` passing (includes the new admin mapper test). Browser/mobile/Safari QA and a live gateway round trip remain unverified.

- **Issue 02 continued (payment reconciliation).** `redirected`/`verify_error` PaymentIntents only ever moved forward when the buyer clicked their own retry — nothing scheduled ever rechecked them, so an abandoned gateway session could hold inventory indefinitely with zero staff visibility. Shipped in two steps, deliberately *not* an unattended scheduled sweep against live ZarinPal (flagged to the requester as a real decision point — chosen: admin-triggered, not automatic): (1) `81be8a5` gives stuck orders the same "needs attention" highlight `pending_verification` receipts already get in the admin order list; (2) `cb276b7` adds `OrdersService.adminReconcileGatewayPayment()` (`POST admin/orders/:id/payment/reconcile`), reusing the exact `verifyAndApplyGatewayResult` path a customer's own retry already uses. Required `verifyAndApplyGatewayResult` to stop requiring a customer `Actor` (an admin action has none) — it now takes `ownerKey` directly and notifies via `NoticesService.createForOwner`. Tests: `apps/api/src/orders/admin-gateway-reconcile.spec.ts` (7 tests: confirms, stays-ambiguous, redirected-left-alone, redirected-confirms, verify_conflict refused, manual-card refused, no double-verify). Committed on `codex/commerce-inventory-checkout-wt` (forked from `codex/commerce-inventory-checkout` after a shared-checkout collision — see note at the end of this section).
- **Issue 03 (cart counters) — investigated, found already unified; one symmetry gap fixed.** All three cart-count display sites (header badge, cart page, checkout bag step) already read a single `useCart()` context backed by one `CartProvider` at the root layout; no duplicated counting logic exists. The one real gap: `placeOrder` dispatches a `"rad:session"` event that resyncs the cart (same mechanism login/logout use), but `confirmDemoPayment`/`verifyPayment`/`retryPayment`/`cancelOrder` did not — harmless today only because checkout already clears the cart before redirecting to the gateway, which is a fragile thing to rely on. All four now dispatch the same event for symmetry. Not independently unit-tested: no React component/hook test harness exists in this repo. Verified by typecheck, lint, and the existing storefront suite (unaffected). Committed on `codex/commerce-inventory-checkout-wt`.
- **Issue 04 (PDP performance) — investigated, no safe fix shipped.** Measured against a production build (`next build`/`next start`) in an isolated sandbox: server TTFB for `/products/[slug]` is ~25-65ms (not a bottleneck), data-fetching is already parallelized and deduped (`resolveWork` wrapped in React's `cache()`, `Promise.all` across FAQ/QR/catalog), and the hero image already uses `next/image` with `priority` set correctly for LCP. The one real lever found: every component under `features/product-detail/` (19 files) is a client component, inflating hydration JS; 8 of them (756 lines: story, care, anatomy, record-cards, specs, questions, making, work-stroke) have zero interactivity of their own and are client-only solely because they call `useLocale()` (a React Context hook). Converting them to server components would require restructuring how locale/translation copy reaches these components (props from a server parent instead of a client context) — a cross-cutting i18n change, not a safe isolated fix, so it was not attempted here. No before/after measurement could be taken for a fix that wasn't made. Flagged as a scoped follow-up, not closed.

## Implemented commerce changes

- Cart hold and cart insertion now share one transaction and a product row lock. Concurrent same-owner adds succeed with one cart row; failed insertion rolls back the reservation.
- Products belonging to active orders cannot be re-added to a cart. Removing old cart rows cannot release order-owned inventory.
- Checkout checks active orders after locking products, preventing duplicate orders from concurrent requests that read the same old cart.
- Automatic expiry excludes redirected, submitted, verified, verify-error and verify-conflict payments. The product sweep also preserves active order inventory.
- Cart holds remain 15 minutes; the existing payment deadline remains 30 minutes. Unpaid abandoned carts and ordinary unpaid orders still expire.

Files: `apps/api/src/cart/cart.service.ts`, `apps/api/src/inventory/inventory.service.ts`, `apps/api/src/inventory/const/product-status.ts`, `apps/api/src/inventory/commerce-recovery.spec.ts`.

Frontend impact: no UI or API contract changes. Backend impact: atomic cart operations and safer reservation ownership. Database impact: existing tables and constraints only; no schema migration.

## Remaining commerce risks

1. An unattended `redirected` gateway session now remains reserved rather than being assumed unpaid. A reliable, explicit reconciliation/operator policy is still required before the complete lifecycle can be signed off. Do not release it solely because a deadline elapsed.
2. Status display still uses the existing `sold` plus hold metadata model. This patch does not claim to unify Admin and Storefront badges.
3. Existing cancel/late-callback behavior remains unchanged; a late captured payment can enter `verify_conflict` and needs operator refund/reconciliation.
4. Request ordering in the cart provider, session changes, old slug resolution, stale product data and checkout/cart concurrent mutation paths need further testing.
5. The initial checkout had unrelated edits in `scripts/production/make-manifest.py` and `scripts/production/rad_release.py`. They are preserved and excluded from this PR.
